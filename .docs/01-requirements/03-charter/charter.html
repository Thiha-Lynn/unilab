🔒 In one sentence. UniLab lets a student finish an everyday file job — compress, convert, scan, trim — entirely inside their own browser, so the file never leaves the device and no deletion promise has to be trusted.

🎯 1. Purpose

Our purpose is to let a student finish an everyday file job — shrink a report under a submission size cap, turn an iPhone photo into a JPG a form will accept, scan a transcript, trim a lecture recording — without handing that file to anybody.

UniLab is a free web application in which every tool runs inside the student’s own browser. The file is opened, changed and saved on the student’s own device, and is never uploaded to a server. There is no upload endpoint anywhere in the codebase.

The project exists because the current alternatives ask students to trade custody of their files — and sometimes of their identity documents — for a routine task that does not need a server at all.

💡 Why this framing matters. “Free” cannot be our reason to exist: iLovePDF already gives students a free year of Premium. Custody is the only claim a competitor with a server cannot copy, so every decision in this charter is measured against it.

⚠️ 2. Problem Statement

Students handle files under deadline pressure, usually on a phone, late at night. Three problems stack on top of each other.

Problem 1 — The free tier runs out exactly when the deadline arrives.
The free web tools students reach for ration what they can do: roughly two tasks a day, then a sign-up or a payment prompt, plus size caps and watermarks. The limit is not felt on a quiet afternoon. It is felt at 11pm the night before, with three files still to fix.

Problem 2 — Routine tasks require handing over identity documents.
Applying for a scholarship, a visa or an internship means scanning a transcript, an ID card or a medical certificate. Converting one of those on a free site means uploading an identity document to a service the student does not know. Those services promise deletion after a fixed window — typically two hours — but the student cannot verify the promise was kept, and cannot withdraw the file once it has been sent.

Problem 3 — No single free site covers everything, so students maintain a list.

💡 6. Proposed Solution

Develop a free web application that performs every file transformation inside the browser, using the browser’s own capabilities rather than a server.

Every tool shares one three-stage shell, so learning one tool teaches the student all 58:

StepThe student doesThe system does
1Opens a tool, for example Compress PDFLoads the tool module and shows the uploader stage
2Picks the file from the deviceReads the file in the browser. No request carries file bytes
3Types the target — 5 MB — and reads the live estimateRenders a preview and an estimated output size before anything is committed
4Runs the toolWorks on-device, yielding every ~24 ms so the tab never freezes
5Downloads the result and may press Delete nowHolds the result in memory only, counts down from 30:00, purges on tab close

🔍 The one decision that matters is at step 3. If the estimate already meets the cap, the student continues; if not, they change the target and the estimate re-renders. They never burn a run to find out. Discovering the file is still too big after the run is precisely the failure this design exists to prevent.

🔑 8. User Roles

Visitor (Student) — the only role, and no account exists

  • Open any tool without signing in, registering or providing an email address.
  • Pick a file from their own device.
  • Set options and read the live preview and estimated output size.
  • Run the transformation on their own device.
  • Download the result.
  • Delete the result immediately, or let the 30-minute countdown purge it.
  • Save, export and re-run a multi-step workflow.
  • Install the application for offline use.

🛡️ There is deliberately no administrator, moderator or operator role. The system stores no user data and holds no files, so there is nothing for an administrator to administer. Removing the role removes the risk that comes with it — and removes the insider-access question entirely.

🧾 12. Assumptions

  • Behaviour: students will accept doing the work on their own device in exchange for never uploading the file.
  • Platform: students have a reasonably current browser; Chrome, Edge and Firefox are fully supported and Safari partially.
  • Device: a phone is the primary camera and often the primary computer for the target user.
  • Access: MFU students, including the Burmese-speaking cohort, are reachable on campus for interviews and real-user testing.
  • Environment: submission forms will continue to enforce size caps and format restrictions, so the need for compression and conversion persists.
  • Competitors: free tiers and their fixed-window deletion promises are what students actually encounter today.
  • Compliance: because no file content leaves the device, no data-controller duties attach to file content under PDPA — the compliance position is a property of the architecture rather than of a policy document.
  • Availability: the public repository and the live deployment remain available for the duration of the semester.
  • Honesty: students describe their own file problems accurately during interviews and testing.
